\begin{abstract}
\noindent Decision table testing and boundary value analysis are standard
black-box techniques, but each answers a different question: the decision
table says which combinations of conditions must be tested, and boundary
value analysis says which inputs to use inside each combination. This report
applies both, together with mutation analysis, to two specifications with
multi-variable behaviour: an ATM withdrawal validator with five inputs and a
fixed rule precedence, and a quadratic equation classifier whose central
boundary is the discriminant \(\Delta=b^2-4ac=0\). For each specification the
conditions are written as an extended-entry decision table, infeasible
columns are proved infeasible, the table is collapsed and checked by rule
count, and a test suite is built in four layers: one test per rule,
3-value boundary value analysis on every ordered condition, an explicitly
labelled extension (boundary combinations and don't-care expansion), and
tests added in response to mutation analysis. Both designs were implemented
in C\#, executed, and evaluated with designed mutants and with mutants
generated by Stryker.NET, cumulatively per layer and, for the ATM, against a
size-matched random baseline. In these two small case studies the results
are as follows. In the ATM, one test per rule killed 3 of 13 designed and 14
of 22 tool-generated mutants, and boundary values raised this to 10 and 21;
the same number of random tests from the same rules killed on average 0.06
of the seven designed mutants that the boundary values add. The two modelled
precedence reversals were killed only by the don't-care expansion, and a
wrong modulus of 25{,}000 survived the whole suite. In the quadratic solver,
one test per rule already killed all ten designed mutants with the chosen
nominal inputs and the boundary tests added no kill; neither mutant
population, however, contains a relational fault at the boundaries \(b=0\) and \(c=0\), at which these tests are aimed, and two such faults, executed separately, were killed only by boundary tests.

\medskip
\noindent\textbf{Keywords:} black-box testing; decision table testing;
boundary value analysis; mutation testing; test design
\end{abstract}

\section{Introduction}
\label{sec:intro}
%=================================================================

A black-box test suite has to stand in for an input domain that is far
larger than the suite. Test design techniques make that substitution
defensible by deriving each test from the specification rather than choosing
it ad hoc. Two techniques are particularly common for rule-based
specifications. \emph{Decision table testing} records how combinations of
conditions determine the system's actions and requires every feasible
combination to be tested \cite{jorgensen2021,copeland2004,istqb}.
\emph{Boundary value analysis} (BVA) selects inputs at and next to the
points where a condition changes its truth value, because developers are
more likely to make errors at those values \cite{myers2011,beizer1990,istqb}.

The two techniques are complementary by construction: the table supplies
the rules, BVA the inputs inside them. The coverage criterion of a decision
table names the combinations to be
tested but not the input to use within a combination; a test taken from the
interior of a rule can pass even when the rule's boundary is implemented
wrongly. Conversely, BVA applied variable by variable does not consider
combinations, and in specifications whose conditions relate several inputs
(a balance compared with an amount plus a fee, or a discriminant computed
from three coefficients) a boundary chosen for one variable in isolation is
generally not a boundary of the condition that decides the output. A further
gap concerns the don't-care entries of a collapsed decision table: they
encode which condition is evaluated first, yet the standard coverage
criterion can be met without ever observing that order.

This report addresses the following research questions on two case studies:
\begin{enumerate}[label=\textbf{RQ\arabic*.}]
    \item How are the conditions, rules and infeasible combinations of a
    decision table derived for a specification whose conditions depend on
    several inputs, and how is the completeness of the table checked?
    \item Which test inputs does 3-value BVA add to decision table coverage,
    and which faults do those inputs detect that one test per rule does not?
    \item Which faults require tests beyond the coverage criterion of the
    decision table (boundary combinations, don't-care expansion, mutation
    feedback), and how large is their contribution?
\end{enumerate}

\paragraph{Scope.} The core of the study is decision table testing and
3-value BVA (layers L1 and L2 of \S\ref{sec:meth-suite}). Everything else is
an extension and is labelled as such where it occurs: the refinements of the
minimal decision tables, layer L3 (boundary combinations and don't-care
expansion), layer L4 (mutation feedback), the mutation analysis itself, and
the executed validation.

The two case studies differ in structure but are treated with the same
method:
\begin{enumerate}[label=(\arabic*)]
    \item \textbf{ATM Withdrawal Validation}
    (Section~\ref{sec:atm}) -- a validator with five inputs, mixed numeric
    and categorical domains, a fixed rule precedence, and a fee that couples
    a categorical input to a numeric threshold.
    \item \textbf{Quadratic Equation Solver} (Section~\ref{sec:quad}) -- a
    classifier over \(a,b,c\in\mathbb{Z}\) whose behaviour is decided by the
    case split \(a=0\) and by the sign of the derived quantity
    \(\Delta=b^2-4ac\).
\end{enumerate}

The report is first a test-design document: every condition, rule,
boundary, test case and mutant in the analytical subsections of
Sections~\ref{sec:atm} and~\ref{sec:quad} is derived from the stated
specification, and the mutant-killing claims there are labelled as
\emph{analytically expected}. Each case study then ends with an executed
validation (\S\ref{sec:atm-exec}, \S\ref{sec:quad-exec}): the
specification is implemented, every designed test is executed, the decision
table is executed as an oracle, the analytical mutation matrix is compared
with the kill sets of executable mutant models, and an automated mutation
tool measures a mutation score on a mutant population that was not designed
together with the suites. Apart from two cells of the quadratic Test\(\times\)Mutant matrix, which show executed values and are marked as such, the analytical subsections use no measured number; where they mention an executed result, they refer forward to the executed validation.

Every test case in this report is traceable to a decision rule, a boundary
coverage item, a boundary combination or further point on a derived
boundary, a don't-care expansion, or a mutant that no earlier test kills.
Section~\ref{sec:background} defines the techniques and positions the
report with respect to the sources (\S\ref{sec:bg-related});
Section~\ref{sec:method} describes the method in general terms;
Sections~\ref{sec:atm} and~\ref{sec:quad} apply it;
Section~\ref{sec:discussion} compares the two case studies and draws the
lessons common to both; Section~\ref{sec:limitations} states the
limitations and Section~\ref{sec:conclusion} answers RQ1--RQ3.

\section{Theoretical Background}
\label{sec:background}
%=================================================================

\subsection{Decision Table Testing}
\label{sec:bg-dt}

A decision table records how combinations of conditions determine the
actions a system takes \cite{jorgensen2021,copeland2004,istqb}. Its rows are
\emph{conditions} (predicates over the inputs) and \emph{actions} (the
responses the specification prescribes); each column is a \emph{rule}, which
assigns one entry to every condition and names the actions that follow. The
notation follows the ISTQB syllabus \cite[\S4.2.3]{istqb}:
\(\mathrm{T}\)/\(\mathrm{F}\) for a satisfied or unsatisfied condition and
``\(-\)'' for a condition whose value is irrelevant to the rule's outcome
(a \emph{don't-care} entry). The syllabus uses ``N/A'' for a condition that
is infeasible for a rule; this report needs a different entry, ``n.e.''
(not defined), for a condition that is not defined in a rule's case (the
sign of \(\Delta\) exists only when \(a\ne0\)). A don't-care entry, in
contrast, belongs to a condition that is defined but whose value cannot
change the rule's actions. In a \emph{limited-entry} table every condition entry is
Boolean; in an \emph{extended-entry} table a condition may take one of
several values, for example a range of numbers or an equivalence partition of
an input domain \cite[\S4.2.3]{istqb}.

Three properties of a decision table are checked explicitly in this report.
\begin{enumerate}[label=(\roman*)]
    \item \textbf{Completeness by rule count.} If condition \(c_j\) has
    \(n_j\) possible entries, a full table has \(\prod_j n_j\) columns; when a condition is defined only in some cases, as \(q_4\) in the quadratic solver, the product is taken per case and the cases are added. A
    don't-care entry in a rule stands for every entry of that condition, so
    a rule with don't-care entries on a set \(J\) of conditions covers
    \(\prod_{j\in J} n_j\) columns of the full table. If the rules are
    complete and do not overlap, these counts sum to the number of feasible
    columns; a smaller sum indicates missing rules and a larger sum
    redundant or contradictory ones \cite[Ch.~7]{jorgensen2021}. The
    equality is necessary but not sufficient, since a gap and an overlap can
    cancel; non-overlap is therefore checked separately, by comparing the
    entries of every pair of rules and by execution.
    \item \textbf{Feasibility.} A combination of condition entries is
    \emph{infeasible} when no input satisfies all of them at once, typically
    because the conditions are logically dependent. Infeasible columns are
    removed from the table \cite[\S4.2.3]{istqb}; in this report each removal
    is justified by a short proof, and, where the domain is finite, by an
    exhaustive count showing that no input reaches the column.
    \item \textbf{Collapsing.} Columns that differ only in conditions that do
    not affect the actions are merged into one rule with a don't-care entry
    \cite[\S4.2.3]{istqb}. In the ATM the don't-care entries arise from the
    rule precedence: once a rule has determined the outcome, the conditions
    evaluated after it cannot change it. In the quadratic solver the only
    one arises because \(c\) is irrelevant when \(a=0\) and \(b\ne0\). The result
    of merging every such pair of columns is the \emph{minimal} table. This
    report deliberately keeps some columns with the same actions apart, so
    that each class of an extended-entry condition, or each value of a
    coefficient condition, has a rule and therefore a test of its own; where
    this is done it is stated, together with the size of the minimal table,
    and it is an extension of the technique.
\end{enumerate}

The coverage items of decision table testing are the feasible columns of the
(collapsed) table; full coverage requires at least one test per feasible
column \cite[\S4.2.3]{istqb}. Two consequences of this criterion shape the
construction in Section~\ref{sec:meth-suite}. First, the criterion says which
rule a test must reach but not which input within the rule to use, so a
second technique is needed to choose the input; this report uses nominal
values (\S\ref{sec:bg-norm}) for the first test of each rule and boundary
value analysis (\S\ref{sec:bg-bva}) for the rest. Second, a test of a
collapsed rule fixes each don't-care entry to one concrete value; the
coverage criterion does not require the other values to be tried. Where a
don't-care entry encodes an evaluation order, trying the other value is the
only way to check the order itself; this report adds such tests and labels
them as an extension of the criterion (Layer~L3 in
Section~\ref{sec:meth-suite}).

When a condition is an extended entry whose values are the equivalence
classes of one input, the classes must be mutually exclusive and must cover
the input's domain, as for equivalence partitioning
\cite{myers2011,istqb}; this is what makes the rule count in (i) meaningful.
In this report every extended-entry condition is defined in set notation and
both properties are checked.
\subsection{Boundary Value Analysis}
\label{sec:bg-bva}

Boundary Value Analysis (BVA) \cite{myers2011,beizer1990,istqb} applies to a
condition whose values are ordered, so that its true and false regions are
separated by boundary points. Specifications are mostly written with
relations (\(<\), \(\le\), \(=\), \(\ge\), \(>\)), and the typical defect is a
boundary implemented one step away from its intended position or omitted
\cite[\S4.2.2]{istqb}: an error of \(\le\) for \(<\) is invisible to an input
far from the boundary and visible at the boundary itself.

This report uses \emph{3-value BVA} \cite[\S4.2.2]{istqb}: for each boundary
value \(v\) of a condition, the coverage items are \(v\) and both of its
neighbours. Applied to a closed range \([\mathrm{Min},\mathrm{Max}]\), this
gives the values
\[
\mathrm{Min}^-,\ \mathrm{Min},\ \mathrm{Min}^+,\ \mathrm{Max}^-,\ \mathrm{Max},\ \mathrm{Max}^+,
\]
which, together with a nominal value \(\Norm\), are the values of
\emph{robust} boundary value testing \cite[Ch.~5]{jorgensen2021}. A condition
with a single boundary \(T\) (e.g.\ \(x\ge T\)) has the coverage items
\(T-1\), \(T\), \(T+1\) on an integer domain. Following
\cite[Ch.~5]{jorgensen2021}, boundary tests are built under the
\emph{single-fault assumption}: one condition is placed at or next to its
boundary while every other condition keeps the entry it has in the nominal
test of the same rule. Tests in which two or more conditions are at their
boundaries at the same time are built separately (\S\ref{sec:bg-multi}).

\textbf{Neighbours must be reachable.} ``Neighbour'' means the nearest value
the condition can actually take, which is not always \(v\pm1\). If the valid
values of an input form a lattice (all multiples of a step \(s\)), the
neighbours of a lattice endpoint on the lattice are \(v\pm s\), and the
integers \(v\pm1\) are neighbours on the integer line that fail the lattice
condition; both kinds are listed, because they belong to different
conditions. Likewise, a derived quantity may skip integer values, in which
case its nearest reachable values have to be found before any boundary test
is written (\S\ref{sec:quad-bva}). Choosing an unreachable neighbour yields a
test case that cannot be executed.
\subsection{Nominal Values}
\label{sec:bg-norm}

A nominal (\(\Norm\)) value of a condition entry is a value from the
interior of that entry, away from every boundary, so that it represents the
entry's ordinary behaviour \cite[Ch.~5]{jorgensen2021}. Nominal values serve
two purposes in this report: they are the inputs of the one-test-per-rule
layer, and they fill the conditions that are not under analysis in a
boundary test, so that only the condition under analysis is at its edge.
Some rules have no interior: a rule with a single member, or a
rule defined by an equality such as \(\Delta=0\), has every member on its
boundary. For such rules a nominal value does not exist; this is stated
where it occurs and a canonical member of the rule is used instead. When a
specification has several structurally different valid behaviours, as the
quadratic solver has, one nominal tuple cannot represent all of them, and a
nominal input is defined per rule (\S\ref{sec:quad-norms}).

\subsection{Multi-Variable Boundaries}
\label{sec:bg-multi}

Many specifications decide behaviour by a \emph{relation among several
variables}, e.g.\ \(\mathit{balance}\ge\mathit{amount}+\mathit{fee}\) or the
sign of \(\Delta=b^2-4ac\). Such a relation is called a \emph{derived
boundary} in this report. In a decision table it appears as one condition,
and its boundary values are values of the derived quantity, not of any one
input. Two consequences follow. First, a boundary test of a derived
condition has to be constructed by solving the relation for one input given
the others; varying one input over its own domain boundaries while holding
the others at nominal values does not, in general, reach the derived
boundary at all. Second, several conditions can be at their boundaries at
the same time, and a categorical input can move the boundary of a numeric
condition (the fee selected by \(\mathit{isInternal}\) moves the balance
threshold). A \emph{boundary combination} is a test in which at least two
conditions are at or next to their boundaries at once, or in which a change
of one condition moves the threshold of another while the numeric inputs
stay on that threshold (\S\ref{sec:atm-combos}, \S\ref{sec:quad-combos}).
Because a derived boundary is a surface rather than a point, a single
boundary test samples only one of its points; further points of the same
surface, reached through other combinations of inputs, are a third kind of
test considered in this report.

\subsection{Mutation Testing}
\label{sec:bg-mutation}

Mutation testing \cite{demillo1978,jia2011} evaluates the fault-detection
strength of a test suite. A \emph{mutant} is the specification, or an
implementation of it, with one small fault seeded into it: a relational
operator swapped (\(\ge\to>\)), a boundary constant perturbed
(\(20{,}000{,}000\to19{,}999{,}999\)), a logical connective changed
(\(\text{AND}\to\text{OR}\)), or an arithmetic term altered
(\(b^2-4ac\to b^2-2ac\)). A test \emph{kills} a mutant if the mutant's output
for the test input differs from the specified output; a mutant
\emph{survives} a suite if no test in the suite kills it. The mutation score
is
\[
\text{Mutation Score} = \frac{\text{killed non-equivalent mutants}}
{\text{all non-equivalent mutants}} \times 100\,\%,
\]
where an \emph{equivalent mutant} computes the same output as the original
for every input of the domain, so that no test can kill it, and is excluded
from the denominator. In the analytical subsections of
Sections~\ref{sec:atm} and~\ref{sec:quad}, kill claims are
\textbf{analytically expected}: they are derived by substituting each test
input into the specification and into the mutant. Measured results, obtained
by executing mutants, are reported separately in \S\ref{sec:atm-exec} and
\S\ref{sec:quad-exec}.

\subsection{Related Work and Positioning}
\label{sec:bg-related}

\paragraph{What the sources establish.} Decision table testing and boundary
value analysis are standard black-box techniques with stated coverage
criteria. The ISTQB syllabus defines the coverage items of decision table
testing as the feasible columns of the table and those of BVA as the
boundary values of ordered partitions and, in the 3-value variant, their
neighbours \cite[\S\S4.2.2--4.2.3]{istqb}. Jorgensen and DeVries describe
decision-table-based testing, including don't-care entries and the rule
count, and several forms of boundary value testing: normal, robust, and
\emph{worst-case}, in which all combinations of the boundary values of
several variables are tested \cite[Ch.~5, Ch.~7]{jorgensen2021}. Copeland
presents boundary value testing and decision table testing as separate
techniques \cite[Ch.~4, Ch.~5]{copeland2004}. Two older methods combine
input classes with conditions: cause-effect graphing derives a decision
table from the causes and effects of a specification and complements it with
boundary analysis \cite{myers2011}, and the category-partition method
derives test frames from categories of input values and constraints between
them \cite{ostrand1988}. Boundaries of predicates over
several variables are the subject of domain testing, which selects ON points
on a border and OFF points next to it \cite{whitecohen1980}
\cite[Ch.~8]{copeland2004}. For evaluating suites, mutation analysis
\cite{demillo1978,jia2011} is supported by evidence that the detection of
generated mutants correlates with the detection of real faults
\cite{andrews2005,just2014}; the correlation, however, becomes weak once
suite size is controlled \cite{papadakis2018}, equivalent mutants must be
identified, and a mutant population reflects the operators that produced it
\cite{jia2011}.

\paragraph{What they leave open.} In these sources decision tables and BVA
are presented as separate techniques, each with its own coverage criterion
\cite[\S\S4.2.2--4.2.3]{istqb} \cite[Ch.~4, Ch.~5]{copeland2004}. The decision
table criterion names the columns to exercise but not the input to choose
within a column, and the ISTQB definition admits equivalence partitions as
condition values without prescribing which member to test
\cite[\S4.2.3]{istqb}. Domain testing treats multi-variable borders, but not
the rules and evaluation order of a decision table, and a collapsed table
records an evaluation order only implicitly, in its don't-care entries.

\paragraph{Where this report sits.} This report does not propose a new
technique. It applies the standard techniques together on two worked case
studies and makes their interaction explicit: BVA is applied to the
conditions of the decision table, including derived conditions over several
inputs, inside the rules in which each condition decides the outcome; the
boundary tests of derived conditions are ON and OFF points in the sense of
domain testing; boundary combinations resemble worst-case boundary value
testing in that several conditions are placed at boundaries together, but
they use the thresholds of derived conditions rather than products of
single-variable boundary values; and the don't-care entries are
expanded where they encode an evaluation order. The contribution of each of
these steps is then measured on designed and on tool-generated mutants, and
against a random baseline of the same size, so that the claims about what
each layer adds rest on observed kills rather than on the definitions alone. Reid \cite{reid1997} compared boundary value analysis empirically with equivalence partitioning and random testing; the size-matched random baseline of this report is a comparison of the same kind.

\section{Methodology}
\label{sec:method}
%=================================================================

Both case studies follow the same five design stages
(\S\S\ref{sec:meth-spec}--\ref{sec:meth-mut}), and both designs are then
validated by a sixth, executed stage (\S\ref{sec:exec-method}).

\subsection{From Specification to Domain}
\label{sec:meth-spec}
Each case study begins with an informal problem statement, which is first
made precise as a \emph{formal specification}: a function signature (named
inputs with types), a set of explicit constraints (inequalities, equalities,
categorical memberships), and an explicit, enumerated output domain
\(D_{out}\). Every input's domain \(D_i\) is stated explicitly (e.g.\
\(\mathit{amount}\in\mathbb{Z}\),
\(\mathit{accountStatus}\in\{\mathrm{Active},\mathrm{Frozen}\}\)), and every
assumption the problem statement leaves open is stated as such.

\subsection{Decision Table Construction}
\label{sec:meth-dt}
Each business rule or case distinction of the specification becomes a
condition of a decision table, and each element of \(D_{out}\) becomes an
action. A condition over a single input with more than two behaviourally
different regions (e.g.\ an amount that can be too small, valid, malformed
or too large) is written as an extended-entry condition whose entries are
those regions, each defined in set notation and checked to be mutually
exclusive and to cover the input's domain. Conditions over several inputs
(e.g.\ \(\mathit{dailyUsed}+\mathit{amount}\le 20{,}000{,}000\), or the
sign of \(\Delta=b^2-4ac\)) are kept as conditions in their own right,
because they are the predicates the specification actually evaluates. The
full table is then built, infeasible columns are identified and proved
infeasible, columns whose outcome does not depend on a condition are
collapsed into one rule with a don't-care entry, and the rule count is
checked against the number of feasible columns (\S\ref{sec:bg-dt}).

\subsection{Boundary Identification}
\label{sec:meth-bva}
For every ordered condition of the table, the boundary values are read from
the specification: the constants of its inequalities and equalities, never
values introduced by the tester. For each boundary value the 3-value BVA
coverage items are listed (\S\ref{sec:bg-bva}). For conditions whose values
are not dense on the integers (a lattice of valid amounts, or a discriminant
that skips some integers) the neighbours are the nearest \emph{reachable}
values, established by an explicit argument. Categorical conditions have no
order and therefore no boundary values; each of their entries is covered by
the decision table layer.

\subsection{Test Suite Construction}
\label{sec:meth-suite}
The suite is built in four layers, in this order. Each test is assigned to
the first layer that requires it and carries a traceability record: its
layer, the decision rule it exercises, the boundary or combination it
targets, and its expected output.
\begin{description}[style=nextline,leftmargin=1.2em]
    \item[L1 -- Decision table coverage.] One test per feasible rule of the
    collapsed table, using the rule's nominal input. This is the coverage
    criterion of decision table testing \cite[\S4.2.3]{istqb}. Where a rule
    has no interior (\S\ref{sec:bg-norm}), this is stated and a canonical
    member of the rule is used.
    \item[L2 -- Boundary values of the conditions.] 3-value BVA on every
    ordered condition, inside each rule in which that condition decides the
    outcome, under the single-fault assumption. A condition evaluated in
    two columns with different thresholds (e.g.\ the balance condition with
    and without a fee) is analysed in each column.
    \item[L3 -- Extension: combinations and don't-care expansion.] Tests that
    the coverage criterion of decision table testing does not require.
    L3a: boundary combinations and further points on a derived boundary
    (\S\ref{sec:bg-multi}). L3b: don't-care expansion, in which the
    don't-care entry of the rule evaluated next in an evaluation order is
    set to its failing entry, so that the order becomes observable. This
    layer goes beyond the coverage criterion and is reported separately.
    \item[L4 -- Mutation feedback.] Tests added only because the mutation
    analysis (\S\ref{sec:meth-mut}) found a designed mutant that layers
    L1--L3 do not kill.
\end{description}
Within a layer, no two tests share their rule, boundary coverage item and
combination; a coverage item already exercised by an earlier layer is not
repeated as a test of its own (it may reappear as one step of a sequence
whose purpose is the sequence, as in the crossing test QC1 of
\S\ref{sec:quad-combos}).

\subsection{Mutation Analysis}
\label{sec:meth-mut}
Mutants are defined for each case study, one per plausible implementation
slip suggested by the specification's own operators, constants, conditions
and evaluation order. Each mutant is checked against the suite by
substitution, producing a Test\(\times\)Mutant matrix with the cells
\texttt{K} (killed), \texttt{S} (the mutated rule is reached but the output
is unchanged) and \texttt{--} (the mutated rule is not reached). A mutant
that no test of layers L1--L3 kills, and that is not equivalent, is the
trigger for a Layer~L4 test.

\subsection{Executed Validation}
\label{sec:exec-method}
Stages~\ref{sec:meth-spec}--\ref{sec:meth-mut} produce a design whose
mutant-killing claims are analytically expected. The executed stage checks
that design against an implementation of the specification. Both
specifications were implemented in C\# on .NET~10 (SDK 10.0.401, runtime
10.0.12, Windows~11). Tests are written with xUnit.net
v3\footnote{\url{https://xunit.net}} (package \texttt{xunit.v3.mtp-v2}
4.0.1) on the Microsoft Testing
Platform\footnote{\url{https://learn.microsoft.com/dotnet/core/testing/microsoft-testing-platform-intro}},
property-based tests with FsCheck~3.4.0\footnote{\url{https://fscheck.github.io/FsCheck}},
a .NET implementation of the QuickCheck approach \cite{claessen2000}, and mutation
testing uses Stryker.NET~5.0.0\footnote{\url{https://stryker-mutator.io}} with
its Microsoft Testing Platform runner, the default mutation level, and the
option \texttt{disable-bail}, so that every test is run against every mutant
and the set of tests that kill each mutant is complete. With this option
every mutant also runs the exhaustive quadratic sweeps; under the default
time limit some of these runs exceed the limit and are reported as timeouts
instead of being classified, so the quadratic runs use an additional
per-mutant time limit of 60~s (\texttt{additional-timeout}), while the ATM
runs use the default. No reported run contains a timeout or a compile
error. The Stryker configuration files and a small program that counts the
mutants killed by the designed suite in a Stryker report
(\texttt{tools/StrykerDesignedKills.cs}) are part of the repository (Data
and code availability). Every number reported in
\S\ref{sec:atm-exec} and \S\ref{sec:quad-exec} comes from the runs of
3~October~2026 on the final test projects (clean Release build, compiler
warnings treated as errors) and is asserted by a test or read from a tool
report; none is estimated. The random baseline uses the fixed seed
\texttt{20261002}; FsCheck draws new random cases on each run, and no
reported number depends on them. The executed stage consists of six checks
per case study:

\begin{enumerate}[label=(\roman*)]
    \item \textbf{Suite execution.} Each designed test case is one test
    (one data row, or for the crossing sequence TC-QE-28 two facts) that
    carries its identifier (TC-ATM-\(nn\), TC-QE-\(nn\)) and its layer, rule,
    boundary and combination as test metadata, so that a run can be filtered
    by, e.g., layer L3 or rule DR5 alone; L3a and L3b are distinguished by
    the combination label (AC or AX). Supplementary tests (SUP-ATM-\(nn\),
    SUP-QE-\(nn\) and a few guard tests) cover the implementation's handling
    of inputs outside the specified domain and values that the design does
    not need.
    \item \textbf{Decision table checks.} The decision table is executed as
    an oracle. For the ATM, one witness input is constructed for each of the
    56 feasible columns of the full table; for the quadratic solver, every
    triple of the test range is evaluated against all rules. The checks
    confirm that every executed input matches exactly one rule and that the
    implementation returns that rule's action; for the quadratic solver they
    also confirm that no input reaches an infeasible column.
    \item \textbf{Matrix reproduction.} Each designed mutant is implemented
    in an executable reference model of the specification that injects
    exactly one mutant. The model is first checked to agree with the
    specification and the implementation on every suite row. For each
    mutant, the set of suite tests whose output differs from the unmutated
    model is then compared with the \texttt{K} cells of that mutant's column
    in the analytical matrix, transcribed verbatim. Execution distinguishes
    \texttt{K} from the other two codes; the split between \texttt{S} and
    \texttt{--} remains analytical.
    \item \textbf{Layer ablation.} The designed mutants and the
    tool-generated mutants are evaluated against the cumulative layers, and
    the designed mutants also against each layer alone and against a
    size-matched random baseline (\S\ref{sec:atm-exec}).
    \item \textbf{Tool-generated mutants.} Stryker.NET generates mutants from
    the implementation's source code with its standard operators. Unlike the
    designed mutants, this population was not constructed together with the
    suites (but see the limitations in Section~\ref{sec:limitations}).
    \item \textbf{Properties and exhaustive execution.} FsCheck checks
    invariants and metamorphic relations \cite{chen2018} on 1{,}000 (ATM) or 2{,}000
    (quadratic) generated cases per property; for the quadratic solver, the
    classifier is executed on the whole test range.
\end{enumerate}

\section{Case Study I: ATM Withdrawal Validation}
\label{sec:atm}
%=================================================================

\subsection{Problem Context}
\label{sec:atm-context}
An ATM must decide, for a single withdrawal request, whether to approve it or
reject it, and if rejecting, for which single, well-defined reason. The
decision depends on five inputs that interact: the account's monetary state
(current balance, amount already withdrawn today), the requested amount, the
account's administrative state (active or frozen), and whether the
transaction is being made at the bank's own (``internal'') ATM network or a
foreign (``external'') one, which determines whether a fee is charged.

\subsection{Formal Specification}
\label{sec:atm-spec}

\begin{equation}
\mathit{Withdraw}(\mathit{balance},\ \mathit{dailyUsed},\ \mathit{amount},\
\mathit{accountStatus},\ \mathit{isInternal}) \to D_{out}
\end{equation}

with input domains

\begin{gather*}
\mathit{balance}\in\mathbb{Z},\quad
\mathit{dailyUsed}\in\mathbb{Z}_{\ge0},\quad
\mathit{amount}\in\mathbb{Z},\\
\mathit{accountStatus}\in\{\mathrm{Active},\mathrm{Frozen}\},\quad
\mathit{isInternal}\in\{\mathrm{True},\mathrm{False}\}.
\end{gather*}

\textbf{Assumptions of this report.} The problem statement leaves three
points open; each is settled by an explicit assumption.
\begin{description}[style=nextline,leftmargin=1.2em]
    \item[(AS1) Balance.] \(\mathit{balance}\in\mathbb{Z}\) is an unbounded
    signed integer: an account may be overdrawn, and no upper bound is given.
    Designed test values stay within the 32-bit signed range.
    \item[(AS2) Amount withdrawn today.] \(\mathit{dailyUsed}\in\mathbb{Z}_{\ge0}\):
    it is a running total of the day's withdrawals, which only adds
    non-negative amounts to a counter that starts at \(0\). Negative values
    are outside the domain rather than a separate rejection case.
    \item[(AS3) Evaluation order.] When several rules fail, the order below
    decides which rejection is reported.
\end{description}

\textbf{Business rules.} R1, R2, R3 and R5 are predicates; R4 defines the
fee used by R5.
\begin{align}
\text{(R1) Status:}\quad & \mathit{accountStatus}=\mathrm{Active} \\
\text{(R2) Amount range \& granularity:}\quad &
50{,}000 \le \mathit{amount} \le 20{,}000{,}000 \notag\\
&\quad{}\wedge\ \mathit{amount}\equiv 0 \pmod{50{,}000} \\
\text{(R3) Daily limit:}\quad & \mathit{dailyUsed}+\mathit{amount} \le 20{,}000{,}000 \\
\text{(R4) Fee:}\quad & \mathit{fee}=
\begin{cases} 0, & \mathit{isInternal}=\mathrm{True}\\
50{,}000, & \mathit{isInternal}=\mathrm{False}\end{cases} \\
\text{(R5) Balance:}\quad & \mathit{balance}\ge \mathit{amount}+\mathit{fee}
\end{align}

\textbf{Output domain.}
\begin{multline*}
D_{out}=\{\mathrm{Approved},\ \mathrm{Rejected\_InvalidAccount},\
\mathrm{Rejected\_InvalidAmount},\\
\mathrm{Rejected\_DailyLimit},\
\mathrm{Rejected\_InsufficientBalance}\}
\end{multline*}

\textbf{Precedence (AS3).} The validator evaluates the rules in a fixed
order and returns on the first failure:
\[
\text{R1} \;\to\; \text{R2} \;\to\; \text{R3} \;\to\; \text{R5}
\;\to\; \mathrm{Approved}.
\]
Some fixed order is required, because otherwise an input that fails several
rules has no single specified output. This report chooses the order above:
the account status is checked before any amount; the amount is checked
before the sums that use it; and the daily limit, a policy of the bank, is
checked before the customer's balance. Other orders would be equally
consistent, and would change only the outputs of inputs that fail more than
one rule. In the decision table (\S\ref{sec:atm-dt}) the order appears as
don't-care entries, and it is exercised by the don't-care expansion tests
(\S\ref{sec:atm-combos}), in which two adjacent rules fail at the same time.

\label{sec:atm-domains}

The approved inputs are those for which R1, R2, R3 and R5 hold together; the
decision table states this region explicitly (\S\ref{sec:atm-dt}).

\subsection{Decision Table}
\label{sec:atm-dt}

\paragraph{Conditions.} The specification evaluates four predicates (R1,
R2, R3, R5) and one categorical input that selects the fee (R4). R2 can fail
in three different ways (amount too small, not a multiple of the step, too
large), so it is written as an extended-entry condition whose four entries
are the following classes of \(D_{\mathit{amount}}=\mathbb{Z}\):
\begin{align}
A_1 &= \{x\in\mathbb{Z}\mid x<50{,}000\}, \\
A_2 &= \{x\in\mathbb{Z}\mid 50{,}000\le x\le 20{,}000{,}000\ \wedge\ x\equiv 0 \!\!\!\pmod{50{,}000}\}, \\
A_3 &= \{x\in\mathbb{Z}\mid 50{,}000\le x\le 20{,}000{,}000\ \wedge\ x\not\equiv 0 \!\!\!\pmod{50{,}000}\}, \\
A_4 &= \{x\in\mathbb{Z}\mid x>20{,}000{,}000\}.
\end{align}
\(A_2\) and \(A_3\) split the closed range by the modulus condition, and
\(A_1\), \(A_4\) cover everything outside it, so the four classes are
mutually exclusive and \(A_1\cup A_2\cup A_3\cup A_4=\mathbb{Z}\). Only
\(A_2\) satisfies R2. Table~\ref{tab:atm-conditions} lists the five
conditions and the two actions.

\label{sec:atm-bva}

Boundary values are taken only from the boundaries the specification states:
the two ends of the amount range and its granularity (R2), the daily limit
(R3) and the balance threshold (R5). \(c_1\) and \(c_4\) are unordered
categorical conditions, so BVA does not apply to them; each of their entries
is already exercised by the L1 tests of the rules in
Table~\ref{tab:atm-dt}. All tests below keep every condition other than the
one under analysis at the nominal entry of its rule (\S\ref{sec:atm-nominal}).

\paragraph{Amount (\(c_2\)).} R2 is the conjunction of a range condition on
the integer line and a granularity condition. The valid amounts are the
lattice \(A_2=\{50{,}000,\,100{,}000,\,\dots,\,20{,}000{,}000\}\) with step
\(s=50{,}000\), so the two ends of the range have neighbours of two kinds
(\S\ref{sec:bg-bva}): integer neighbours (\(\pm1\)), which leave \(A_2\)
through the granularity condition or the range condition, and lattice
neighbours (\(\pm s\)), which are the nearest amounts that pass the
granularity condition. 3-value BVA is applied on both: each end of the range
gets its integer neighbours and its lattice neighbours, so that each end has
five coverage items instead of three. Table~\ref{tab:atm-amount-bva} lists
them; ``Norm'' is the nominal amount \(500{,}000\) of TC-ATM-07.

beyond the coverage criterion of decision table testing. It has two parts,
L3a and L3b.

\subsection{Test Suite Construction}
\label{sec:atm-suite}

The suite was built in the four layers of \S\ref{sec:meth-suite}.
\begin{description}[style=nextline,leftmargin=1.2em]
    \item[L1 (9 tests, TC-ATM-01--09).] One test per rule DR1--DR9 of
    Table~\ref{tab:atm-dt}. Each starts from the nominal configuration
    (Table~\ref{tab:atm-nominal}) and changes only what its rule requires
    (Table~\ref{tab:atm-l1}).
    \item[L2 (19 tests, TC-ATM-10--28).] The coverage items of
    Tables~\ref{tab:atm-amount-bva}--\ref{tab:atm-balance-bva}, except the
    nominal values already used by L1 tests.
    \item[L3 (8 tests, TC-ATM-29--36).] The boundary combinations AC1--AC4
    (L3a, Table~\ref{tab:atm-combos}) and the don't-care expansions
    AX1--AX4 (L3b, Table~\ref{tab:atm-dontcare}).
    \item[L4 (1 test, TC-ATM-37).] The tests needed to kill designed mutants
    that L1--L3 leave alive. One such mutant exists: M8, which checks
    divisibility by \(10{,}000\) instead of \(50{,}000\)
    (\S\ref{sec:atm-matrix}). Every amount in L1--L3 that is not a multiple
    of \(50{,}000\) is also not a multiple of \(10{,}000\) (\(25{,}000\),
    \(49{,}999\), \(50{,}001\), \(512{,}345\), \(19{,}999{,}999\),
    \(20{,}000{,}001\)), so M8 rejects all of them for the same reason as the
    specification. TC-ATM-37 uses \(60{,}000\), a multiple of \(10{,}000\) but
    not of \(50{,}000\).
\end{description}

\paragraph{A granularity slip that the suite does not expose.} M8 is one of
several possible wrong moduli. Replacing \(50{,}000\) by a divisor \(d\) of
it changes R2 only for in-range amounts that are multiples of \(d\) but not
of \(50{,}000\). Every divisor of \(10{,}000\) is exposed by TC-ATM-37, but
the divisors of \(25{,}000=50{,}000/2\) that do not divide \(10{,}000\), such
as \(25{,}000\) and \(12{,}500\), are exposed by no designed test: no amount
of the suite is an odd multiple of \(25{,}000\) inside the range. An amount
such as \(75{,}000\) would be needed. This follows by substitution of the
suite's amounts and is confirmed by execution in \S\ref{sec:atm-exec}; it shows that a mutation-feedback
test protects against the mutant it was added for, not against the whole
class of similar faults.

\textbf{Discussion of the columns.} The mutants fall into four groups,
according to the kind of test that kills them.

\emph{Equality-boundary mutants (M1, M2, M3).} Each changes the outcome only
for inputs that lie exactly on a boundary, so each is killed exactly by the
tests that sit on that boundary. M1 (R5 strict) is killed by the five tests
with \(\mathit{balance}=T_5\): TC-ATM-24 and TC-ATM-27 (the \(T_5\) items of
the internal and external columns) and the combinations TC-ATM-29--31. M2
(R3 strict) is killed by the four tests with a daily sum of exactly
\(20{,}000{,}000\): TC-ATM-17, -21, -30 and -31; TC-ATM-22 and TC-ATM-36,
whose sum is \(20{,}000{,}001\), are rejected identically by the original
and the mutant. M3 (upper bound \(19{,}999{,}999\)) is killed by the two
tests with \(\mathit{amount}=20{,}000{,}000\), TC-ATM-17 and TC-ATM-30. No
L1 test kills any of the three, because every L1 input is a nominal value
away from all boundaries.

\emph{Threshold-magnitude mutants (M6, M7, M10, M13).} These move a
threshold by a fixed amount. They are killed only by a test placed between
the correct and the mutated threshold. M7 (external fee \(5{,}000\), so
\(T_5=505{,}000\)) is killed only by TC-ATM-26 (\(549{,}999\)); TC-ATM-32
(\(500{,}000\)) and TC-ATM-08 (\(100{,}000\)) lie below both thresholds. M6
(fee removed, \(T_5=500{,}000\)) is killed by TC-ATM-26 and TC-ATM-32. M13
(fee \(100{,}000\), \(T_5=600{,}000\)) is killed by TC-ATM-27 and TC-ATM-28,
the external \(T_5\) and \(T_5+1\) items. M10 (lower amount bound \(0\)) is
killed only by TC-ATM-10: the mutant accepts exactly the multiples of
\(50{,}000\) in \([0,50{,}000)\), i.e.\ the amount \(0\), and \(0\) is the
only amount below the range in the suite that is a multiple of
\(50{,}000\); the other amounts below the range (\(25{,}000\), \(49{,}999\))
fail the granularity condition and are rejected by the mutant as well. All four are killed by L2 tests derived from the
\(T_5-1\), \(T_5\), \(T_5+1\) items of the external column and from the
lattice item \(\mathrm{Min}^-\).

\emph{Precedence mutants (M11, M14).} They swap two adjacent rules. With at
most one failing rule, either order reports the same reason, so each is
killed only by a test in which both rules of its pair fail: M11 (R3/R5) by
TC-ATM-36 and M14 (R1/R2) by TC-ATM-33, the don't-care expansions AX4 and
AX1, which were constructed to make exactly these pairs fail; their kills
are therefore by construction. No test of the decision table coverage layer
or the boundary layer kills them: the only tests of those layers in which
two rules fail are TC-ATM-04, -18 and -19 (an amount above the range with
\(\mathit{dailyUsed}=0\), so R2 and R3 fail, and for TC-ATM-04 also R5), and
neither M11 nor M14 concerns that pair. The third adjacent reversal, R2/R3,
is not among the designed mutants; by substitution it would already be
killed by TC-ATM-04, -18 and -19, because the rule DR4 forces
\(c_3=\mathrm{F}\) for every amount above the range. The claim that only the
don't-care expansion exposes a reversed precedence therefore holds for the
two modelled pairs, not for every pair; all six transpositions of two checks
are executed in \S\ref{sec:atm-exec}.

\emph{Coarse mutants (M5, M9, M12).} These change the outcome for whole
regions of a rule, so any test that reaches the mutated rule in such a
region kills them. M9 (status condition reversed) is
killed by all 37 tests: on the 35 tests with an active account it reports
Rejected\_InvalidAccount immediately; on TC-ATM-01 it approves a frozen
account, and on TC-ATM-33 it passes R1 and reports Rejected\_InvalidAmount.
M5 (R1/R2 gate weakened to OR) is killed by the 13 tests in which exactly
one of R1, R2 fails; on TC-ATM-01, for example, the frozen account proceeds
to R3 and R5 and is approved. It survives TC-ATM-33, where both fail and the
mutant reports the same reason as the specification. M12 (amount dropped
from the daily sum) is killed by the three tests with
\(\mathit{dailyUsed}\le20{,}000{,}000<\mathit{dailyUsed}+\mathit{amount}\)
that reach R3: TC-ATM-05, -22 and -36. These three mutants are the only
ones that the L1 tests already kill.

M8 (divisibility by \(10{,}000\)) is the one mutant that no test of L1--L3
kills; the L4 test TC-ATM-37 (\S\ref{sec:atm-suite}) exists for this reason
and is, by construction, the only test that kills it.

\textbf{Equivalent mutant.} M4 raises the upper amount bound to
\(20{,}000{,}001\). Every amount accepted by R2 is a multiple of
\(50{,}000\), and \(20{,}000{,}001\) is not, so the mutated range admits no
additional valid amount: M4 computes the same output as the specification for
every input of the domain, not only for the inputs of this suite, and is
excluded from the denominator of the mutation score (\S\ref{sec:bg-mutation}).
The other thirteen mutants are each killed by at least one test, so the
analytically expected score of the suite is \(13/13\). This is a property of
the design against the stated specification; its executed confirmation, and
a score measured on an independent mutant population, are reported in
\S\ref{sec:atm-exec}. The designed mutants were written with knowledge of the
boundaries the suite targets (Section~\ref{sec:limitations}), so the full
score is not, by itself, evidence that boundary tests are generally stronger
than interior ones.
\subsection{Executed Validation}
\label{sec:atm-exec}

This subsection reports the executed stage of \S\ref{sec:exec-method} for the
ATM validator.

\paragraph{Implementation decisions.} The specification leaves two points
open, so the implementation makes an explicit choice for each and tests it.
First, \(\mathit{dailyUsed}<0\), which AS2 excludes from the domain, raises
an argument-range error instead of returning an element of \(D_{out}\); this
check runs before R1, so a frozen account with a negative
\(\mathit{dailyUsed}\) also raises it. Second, R3 is evaluated in the
rearranged form \(\mathit{dailyUsed}>20{,}000{,}000-\mathit{amount}\). It is
equivalent to R3 for every input that reaches it (R2 has already bounded
\(\mathit{amount}\)), but unlike the direct sum it cannot overflow when
\(\mathit{dailyUsed}\) is close to the largest representable integer; the
specification does not address overflow.

\paragraph{Suite execution.} All 131 ATM tests pass: the 37 designed tests
TC-ATM-01--37, 12 supplementary tests (domain guards, overflow extremes, an
undefined status value, a negative balance, a negative amount and two
further daily-limit values), 5 decision table checks, 65 matrix-reproduction
checks (including the four granularity checks of \S\ref{sec:atm-suite} and the seven precedence-transposition checks below), 4
layer-ablation checks and 8 properties (Table~\ref{tab:emp-layers}).

\paragraph{Decision table checks.} The 56 feasible columns of the full table
are executed with one witness input each. Every witness matches exactly one
collapsed rule, and the implementation returns that rule's output for all
of them; the rules stand for \(28+8+8+4+4+4=56\) feasible columns, as
derived. Witnesses are constructed per column, so this check tests the
implementation against the table, not the table itself. The eight columns
with \(c_2=A_4\) and \(c_3=\mathrm{T}\) are infeasible by the argument of
\S\ref{sec:atm-dt} and are not executed. Every designed test belongs to the
rule recorded for it in Table~\ref{tab:atm-suite}.

\paragraph{Matrix reproduction.} The analytical matrix of
Table~\ref{tab:atm-matrix} was derived by substitution, without executing the
mutant models, and is compared with the executed kill sets: in all
\(37\times14=518\) cells, an analytical \texttt{K} coincides with an executed
kill and every \texttt{S} or \texttt{--} with an executed survival. The
executed score is therefore \(13/13\) non-equivalent designed mutants. The
equivalence of M4 is additionally checked by executing the original and M4
for every integer amount in \([-100{,}000,\ 20{,}200{,}000]\)
(\(20{,}300{,}001\) values, all other rules passing); no output differs. Four
further checks confirm the granularity result of \S\ref{sec:atm-suite}: of
the moduli \(10{,}000\), \(5{,}000\), \(25{,}000\) and \(12{,}500\), the first two
are exposed only by TC-ATM-37 and the last two by no designed test.

\subsection{Case Study Discussion}
\label{sec:atm-discussion}

Three observations follow from this case study; the comparison with the
second case study is made in \S\ref{sec:cross-case}.

First, the decision table made the evaluation order of the specification
explicit. The nine collapsed rules close the rule count, and their
don't-care entries mark exactly the conditions whose value the precedence
\(\mathrm{R1}\to\mathrm{R2}\to\mathrm{R3}\to\mathrm{R5}\) makes irrelevant.
The coverage criterion of the table is met by nine tests. They cannot
observe a reversal of R3/R5 or R1/R2, which the two designed precedence
mutants M11 and M14 model; those are killed only by the don't-care
expansions AX4 and AX1 (Table~\ref{tab:atm-ablation}). The other four transpositions of two checks, executed separately, are already exposed by the coverage test of DR4, TC-ATM-04, whose input fails R2, R3 and R5 together; for three of them this holds for every input of DR4, for R1/R5 only because the amount of TC-ATM-04 exceeds the balance (\S\ref{sec:atm-exec}).

Second, the decision table says which combinations must be tested but not
where inside a rule to test them. Its nine nominal tests kill only the three
coarse designed mutants (M5, M9, M12). The boundary values of
\S\ref{sec:atm-bva} kill seven more; on these seven, nineteen random members of the
same rules kill on average 0.06 (\S\ref{sec:atm-exec}). Four of the seven
depend on two details that only the boundary analysis provides: the lattice
neighbour \(\mathrm{Min}^-=0\) (M10), and the analysis of \(c_5\) in the
external column, where the fee moves the threshold to \(550{,}000\) (M6,
M7, M13). The boundary combinations of L3a, in contrast, kill nothing that
L1--L2 do not already kill. The granularity condition remains the weakest
point of the suite: a modulus of \(25{,}000\) survives every test.

Third, a categorical input can change a numeric boundary. \(c_4\)
(\(\mathit{isInternal}\)) never decides an outcome by itself, yet it cannot
be collapsed, because it selects the fee and with it the threshold of \(c_5\)
(Figure~\ref{fig:atm-fee-plane}); the combination AC4 shows the same numeric
input approved in one column and rejected in the other. Independent coverage
of \(\mathit{isInternal}\) and of \(\mathit{balance}\) would not place a test
between the two thresholds.

\section{Case Study II: Quadratic Equation Solver}
\label{sec:quad}
%=================================================================

\subsection{Problem Context}
\label{sec:quad-context}
Given integer coefficients \(a,b,c\), classify the number and nature of the
real solutions of \(ax^2+bx+c=0\). Unlike the ATM case, the three inputs here
are not coupled by separate policy rules but by a single algebraic identity
-- the discriminant -- whose sign alone determines the qualitative output
once the leading-coefficient degeneracy (\(a=0\)) has been handled.

\subsection{Formal Specification}
\label{sec:quad-spec}
\[
\mathit{Solve}(a,b,c) \to D_{out}, \qquad a,b,c\in\mathbb{Z}.
\]

\textbf{Case A --- \(a\ne 0\) (quadratic).} Define \(\Delta = b^2-4ac\).
\begin{align}
\Delta<0 &\Rightarrow \mathrm{NoRealRoots}\\
\Delta=0 &\Rightarrow \mathrm{OneRepeatedRealRoot}\\
\Delta>0 &\Rightarrow \mathrm{TwoDistinctRealRoots}
\end{align}

\textbf{Case B --- \(a=0\) (degenerates to linear \(bx+c=0\)).}
\begin{align}
b\ne 0 &\Rightarrow \mathrm{OneLinearRoot}\\
b=0,\ c\ne 0 &\Rightarrow \mathrm{NoSolution}\\
b=0,\ c=0 &\Rightarrow \mathrm{InfinitelyManySolutions}
\end{align}

\textbf{Output domain.}
\begin{multline*}
D_{out}=\{\mathrm{NoRealRoots},\ \mathrm{OneRepeatedRealRoot},\
\mathrm{TwoDistinctRealRoots},\\
\mathrm{OneLinearRoot},\ \mathrm{NoSolution},\
\mathrm{InfinitelyManySolutions}\}
\end{multline*}

\textbf{Assumptions of this report.}
\begin{description}[style=nextline,leftmargin=1.2em]
    \item[(QS1) Classification only.] The solver reports the real-root
    classification, not the roots; ``no real roots'' covers the whole region
    \(\Delta<0\), since no requirement to report complex roots is given.
    \item[(QS2) Test range.] The specification places no bound on
    \(a,b,c\). The implementation accepts \(a,b,c\in[-100,100]\) and rejects
    other values with an argument-range error, and the exhaustive sweep of
    \S\ref{sec:quad-exec} runs over the cube
    \(D=[-100,100]^3\subset\mathbb{Z}^3\). This range is a property of the
    test environment, not a behavioural rule: no output changes at
    \(\pm100\), so it contributes no condition and no boundary to the design
    (\S\ref{sec:quad-bva}).
\end{description}

\subsection{Constraints and Dependencies}
\label{sec:quad-constraints}

\(a\), \(b\), \(c\) are not independently meaningful to the output: when
\(a\ne0\) the output depends only on the derived quantity
\(\Delta=b^2-4ac\), and when \(a=0\) on a nested case split on \(b\) and
\(c\). This is analogous to the ATM, whose output depends on the derived
quantities \(\mathit{amount}+\mathit{fee}\) and
\(\mathit{dailyUsed}+\mathit{amount}\) rather than on each input alone.

\subsection{Nominal Configurations}
\label{sec:quad-norms}

behaviour (they are separated by \(a=0\)), nor the three signs of \(\Delta\).

\(b=0\). Those boundaries are analysed separately (\S\ref{sec:quad-bva}),
and the effect of the nominal choice on the mutation results is reported in
\S\ref{sec:quad-matrix}.

\subsection{Decision Table}
\label{sec:quad-dt}

\paragraph{Conditions.} The specification evaluates four predicates
(Table~\ref{tab:quad-conditions}): \(q_1\) (\(a=0\)) selects the case; in
Case~B, \(q_2\) (\(b=0\)) and \(q_3\) (\(c=0\)) select the output; in
Case~A, \(q_4\), the sign of \(\Delta\), selects the output. \(q_4\) is an
extended-entry condition whose three entries \(\Delta<0\), \(\Delta=0\),
\(\Delta>0\) are mutually exclusive and exhaust \(\mathbb{Z}\) by
trichotomy. It is evaluated only in Case~A; for the rules of Case~B its entry
is written ``n.e.'' (not defined), which is different from the ISTQB entry
N/A, used there for an infeasible condition \cite[\S4.2.3]{istqb}.

\paragraph{Minimal table.} Read directly from the specification, the table
has six rules: the three rules of Case~B (\(b\ne0\); \(b=0,c\ne0\);
\(b=c=0\)) and one rule per sign of \(\Delta\) in Case~A, in which \(q_2\)
and \(q_3\) are don't-care: they are defined there, but the output of Case~A depends only on the sign of \(\Delta\).

\paragraph{Refined table (extension).} This report refines Case~A by the two
coefficient conditions \(q_2\) and \(q_3\) that the specification evaluates
in Case~B. The refinement is an extension of the minimal table and is
labelled as such: it does not change any output, but it makes the dependence
between \(q_2\), \(q_3\) and \(q_4\) explicit, and it gives the boundaries
\(b=0\) and \(c=0\) rules inside Case~A from which their neighbours can be
taken (\S\ref{sec:quad-bva}). With the refinement, Case~A has
\(2\cdot2\cdot3=12\) columns, and five of them are infeasible:
\begin{itemize}
    \item \(b\ne0,\ c=0\): \(\Delta=b^2>0\), so \(\Delta<0\) and \(\Delta=0\) are infeasible (2 columns);
    \item \(b=0,\ c\ne0\): \(\Delta=-4ac\ne0\) because \(a\ne0\) and \(c\ne0\), so \(\Delta=0\) is infeasible (1 column);
    \item \(b=0,\ c=0\): \(\Delta=0\), so \(\Delta<0\) and \(\Delta>0\) are infeasible (2 columns).
\end{itemize}
The remaining seven columns are feasible; each has a witness in
Table~\ref{tab:quad-dt}. For \(b\ne0,c\ne0\) all three signs occur
(\((1,1,1)\), \((1,2,1)\), \((1,3,2)\)); for \(b=0,c\ne0\) the sign of
\(\Delta=-4ac\) is the opposite of the sign of \(ac\). Case~B has the four
columns of \((q_2,q_3)\); the outcome does not depend on \(c\) once
\(b\ne0\), so two of them collapse into QR1.

\paragraph{Rule count.} The full table has \(4+12=16\) columns, of which
\(5\) are infeasible. The ten rules stand for \(2+1+1\) columns in Case~B and
\(7\) in Case~A, i.e.\ \(2+1+1+7=11=16-5\) feasible columns. This equality is
a necessary condition for completeness without overlap; non-overlap follows
from the rules having pairwise different entries in at least one condition,
and both properties are confirmed by execution over the whole test range
(\S\ref{sec:quad-exec}).

\subsection{Boundary Value Analysis}
\label{sec:quad-bva}

\paragraph{Equality conditions \(q_1\), \(q_2\), \(q_3\).} Each of \(a=0\),
\(b=0\), \(c=0\) partitions an integer coefficient into the ordered classes
\(\{x<0\}\), \(\{0\}\), \(\{x>0\}\), so its boundary value is \(0\) and its
3-value BVA coverage items are \(-1\), \(0\), \(+1\). The item \(0\) is
exercised by the L1 test of every rule whose entry for the condition is T.
The neighbours \(\pm1\) are taken from each such rule, starting from its
nominal input and changing only the coefficient concerned, whenever the
change alters the output. Neighbours that do not alter the output lie in a
rule with the same action and are not used as boundary tests; this is the
case next to QR7 \((1,5,0)\), where \(c=\pm1\) gives \(\Delta=25\mp4>0\),
next to QR8 \((2,0,3)\), where \(b=\pm1\) gives \(\Delta=1-24<0\), and next to
QR9 \((-2,0,3)\), where \(b=\pm1\) gives \(\Delta=1+24>0\).

\(\Delta=0\).} The boundary of \(q_4\) is \(\Delta=0\), a joint condition on
\((a,b,c)\), not a boundary of any one coefficient: the surface
\(b^2-4ac=0\) is two-dimensional inside the three-dimensional input space,
and it can be crossed by changing any one coefficient while the other two
are fixed. Its integer neighbours \(\Delta=\pm1\) are not both reachable.

4\), so
\[

\]

reachable values below and above \(0\) are \(-3\) and \(+1\)
(Table~\ref{tab:quad-reach}). In the rules with \(b=0\), \(\Delta=-4ac\) is
a non-zero multiple of \(4\), so there the nearest reachable values are
\(\pm4\), already exercised by TC-QE-24 and TC-QE-25.

\paragraph{Don't-care expansion.} The only don't-care entry of the refined
table is \(c\) in QR1, which the L1 test fixes to \(c=-4\). Its other entry,
\(c=0\), is already instantiated by the L2 tests TC-QE-18 and TC-QE-19
\((0,\pm1,0)\), so the expansion needs no further test. Unlike the ATM, the
quadratic specification has no evaluation order between failing rules, so
there is no precedence for an expansion to expose.

\paragraph{Single coefficients do not reach \(\Delta=0\).} For fixed \(a\ne0\)
and \(c\), \(\Delta=0\) holds only for \(b=\pm\sqrt{4ac}\), which is an
integer only when \(4ac\) is a perfect square. A value of \(b\) chosen
without reference to \(a\) and \(c\) therefore generally misses the boundary,
and a boundary test of \(q_4\) has to be constructed by solving \(b^2=4ac\)
for one coefficient given the other two, as QR5, QC1, QC2 and QC3 do. The
exhaustive count in \S\ref{sec:quad-exec} quantifies how rarely an
unconstructed input lands on this boundary.

\textbf{Discussion of the columns.} The columns fall into three groups.

\emph{Boundary mutants (N1, N2, N3).} N2 and N3, the relational mutants at
the boundary of \(q_4\), are killed exactly by the six tests that contain an
input with \(\Delta=0\): TC-QE-05, -10, -15, -28 (its middle step), -29 and
-30. They survive every other test, whatever the sign or magnitude of
\(\Delta\). N1 (\(b^2-4ac\to b^2-2ac\)) is killed in this suite by TC-QE-05,
-28, -29 and -30, the \(\Delta=0\) tests with \(ac\ne0\): there \(b^2=4ac\),
so \(\Delta'=b^2-2ac=2ac\ne0\) (at TC-QE-05, \(\Delta'=4-2=2>0\)). It survives
TC-QE-10 and TC-QE-15, where \(ac=0\) and \(\Delta'=\Delta=0\), and every test
with \(\Delta\ne0\), where the sign happens to be preserved (TC-QE-06:
\(\Delta=25\to\Delta'=37\)). This is a property of the suite, not of the
mutant: N1 changes the output of other inputs with \(\Delta\ne0\), e.g.\
\((1,2,2)\), where \(\Delta=-4\) becomes \(\Delta'=0\); the suite contains
no such input.

\emph{Formula mutants (N6, N10).} N6 (\(b^2\to2b\)) is killed only where the
error moves \(\Delta\) across \(0\): TC-QE-06 (\(14-24=-10\)), TC-QE-22
(\(-2-0=-2\)), TC-QE-27 (\(6-8=-2\)) and TC-QE-29 (\(8-16=-8\)). N10
(\(4ac\to4bc\)) survives eight tests for two different reasons: where \(a=b\)
or \(c=0\) the mutation has no numeric effect (e.g.\ TC-QE-04 \((1,1,10)\),
TC-QE-07 \((1,5,0)\)), and at TC-QE-12 \((1,2,-4)\) \(\Delta\) changes from
\(20\) to \(36\) but keeps its sign. It is killed by the other thirteen tests
of Case~A, including the tests with \(b=0\) and \(c\ne0\), where \(4bc=0\)
turns \(\Delta=-4ac\ne0\) into \(0\) (TC-QE-08, -09, -13, -14, -24, -25).

\emph{Branch mutants (N4, N5, N7--N9).} These are killed by any test that
reaches the mutated branch with an output the mutation changes. N4, which
swaps the two classification algorithms, is killed by all 30 tests: no input
yields the same output under the linear rules and under the quadratic rules
with \(\Delta=b^2\). N5 (strict sign labels swapped) is killed by the 16
tests that contain an input with \(a\ne0\) and \(\Delta\ne0\), and survives
the five single-input tests with \(\Delta=0\). N7, N8 and N9 each change one
sub-case of the linear branch and are killed exactly by the tests in that
sub-case: N7 by TC-QE-03; N8 by TC-QE-02, -20 and -21; N9 by TC-QE-01 and
TC-QE-16--19. Every other test is \texttt{--} for them.

No quadratic mutant is equivalent, and each is killed, so the analytically
expected score is \(10/10\).

\textbf{Sensitivity to the nominal inputs.} With the nominal inputs of
Table~\ref{tab:quad-norms}, the ten L1 tests already kill all ten designed
mutants (\S\ref{sec:quad-exec}). For nine of them this follows from the
structure of the table: N1--N3 are killed by the L1 test of QR5, a rule
defined by \(\Delta=0\), and N4, N5, N7--N10 by L1 tests of the branches they
change. N6 is the exception: its only L1 kill is TC-QE-06 \((1,7,6)\), where
\(2b-4ac=-10\) happens to be negative. With another nominal input of QR6 that
is equally far from \(\Delta=0\), such as \((1,9,2)\) (\(\Delta=73\),
\(2b-4ac=10\)), N6 survives all L1 tests, and L1 kills nine of the ten
designed mutants.
\subsection{Executed Validation}
\label{sec:quad-exec}

This subsection reports the executed stage of \S\ref{sec:exec-method} for the
quadratic solver.

\paragraph{Implementation decisions.} Coefficients outside \([-100,100]\)
raise an argument-range error (QS2). For \(a\ne0\), the sign of \(\Delta\) is
classified by testing \(\Delta<0\) first, then \(\Delta>0\), and returning
OneRepeatedRealRoot otherwise; this is the order under which N2 and N3 change
exactly the inputs with \(\Delta=0\) (\S\ref{sec:quad-matrix}). If \(\Delta=0\) were tested first, N2 and N3 would be equivalent mutants, so their kill sets depend on this implementation choice.

supplementary tests (the extremes \(\pm100\) and the out-of-range values

need), 2 decision table checks, 48 matrix-reproduction checks (including the six relational slips below), 3
layer-ablation checks, 6 properties and 2 exhaustive checks
(Table~\ref{tab:emp-layers}).

killed by L1 tests: \(a\ge0\) by every L1 test with \(a>0\), \(b\ge0\) by

TC-QE-09 \((-2,0,3)\), the one L1 test with \(a<0\), a consequence of its nominal value. The other two survive
every L1 test and are killed only by L2 tests: \(b\le0\) by TC-QE-16 and
TC-QE-18, the neighbours \(b=-1\) of QR2 and QR3, and \(c\le0\) by TC-QE-20,
the neighbour \(c=-1\) of QR3. These two faults are detected by the boundary
layer and by no other layer. This does not depend on the nominal inputs: the only L1 tests that reach the tests of \(b\) and \(c\) with a nonzero value are TC-QE-01 (\(b\)) and TC-QE-02 (\(c\)), so whatever sign their nominal values have, the slip in the opposite direction survives L1, and the neighbours \(\pm1\) of L2 kill both directions.

\paragraph{Tool-generated mutants.} Stryker.NET generated 24 mutants; three
were ignored by the tool as redundant block removals, no mutant failed to
compile, and all other 21 were killed (0 survived). This 100\,\% score is the
score of the complete test project; the designed suite alone kills 15 of the
21 (71\,\%). The six it does not kill each remove one of the six
coefficient-range checks; the specification has no such range (QS2), so no
designed test can reach them, and they are killed by the supplementary
tests. The two relational mutants at \(\Delta=0\) (\(\Delta<0\to\Delta\le0\)
and \(\Delta>0\to\Delta\ge0\), the tool-generated counterparts of N3 and N2)
are killed by the designed suite.

The form of the implementation affects which mutants the tool can produce.
If the sign of \(\Delta\) is classified with a relational pattern match
(\texttt{< 0}, \texttt{> 0}, default), the boundary mutants of that form
(\texttt{<= 0}, \texttt{>= 0}) make the default arm unreachable, which the
C\# compiler rejects; the tool then reports them as compile errors and
excludes them from the score, so that a score of 100\,\% no longer covers
the \(\Delta=0\) boundary. The implementation classifies the sign with
if-statements, for which those mutants compile. A measured mutation score is
only as informative as the set of mutants the tool manages to compile.

\paragraph{Exhaustive execution of the test range.} The classifier is
executed on all \(8{,}120{,}601\) triples. It never fails, it agrees with a
re-statement of the specification in arbitrary-precision arithmetic, and
\(\Delta\bmod 4\in\{0,1\}\) for every triple (\S\ref{sec:quad-bva}).

Two claims of this case study can be stated quantitatively over the test
range. First, the reachability argument of \S\ref{sec:quad-bva} holds:
among the \(8{,}080{,}200\) quadratic triples (\(a\ne0\)), discriminants in
\([-4,4]\) occur only as \(-4\) (338 triples), \(-3\) (252), \(0\) (1{,}104),
\(1\) (1{,}880) and \(4\) (1{,}754); \(\Delta\in\{-2,-1,2,3\}\) never occurs.
Second, the boundary \(\Delta=0\) occupies \(1{,}104\) of those
\(8{,}080{,}200\) triples (\(0.0137\,\%\)), \(904\) of them in QR5 and \(200\)
in QR10. A test selected uniformly at random from the quadratic triples hits
it with probability \(1.37\times10^{-4}\), so a random suite of \(1{,}000\)
such tests contains no \(\Delta=0\) case with probability \(\approx0.87\), and
would then kill neither N2 nor N3, which differ from the specification only
at \(\Delta=0\). The specification itself names \(\Delta=0\) as a case of its
own, and the decision table turns it into a rule, so the coverage criterion
requires a test there.
\subsection{Case Study Discussion}
\label{sec:quad-discussion}

The quadratic case study shows a second kind of derived condition. In the
ATM, derived conditions are sums and shifted thresholds; here the central
condition is the sign of a quadratic form, its boundary \(\Delta=0\) is a
curved surface in three dimensions, and its integer neighbours are not all
reachable (\S\ref{sec:quad-bva}). The usual \(\pm1\) neighbours of BVA are
therefore not used for \(q_4\); the nearest reachable values \(-3\) and
\(+1\) take their place.

The decision table played a different role than in the ATM. The minimal
table read from the specification has six rules, and one of them,
\(\Delta=0\), is already a boundary: its coverage test is a boundary test.
The refined table, an extension of this report, splits Case~A by the
coefficient conditions \(b=0\) and \(c=0\); its feasibility analysis shows
how they constrain \(\Delta\) (QR7, QR10) and gives the boundaries \(b=0\) and
\(c=0\) rules inside Case~A from which neighbours are taken. With the chosen
nominal inputs, the L1 tests kill all ten designed mutants; one of these
kills (N6) depends on the nominal value of QR6 (\S\ref{sec:quad-matrix}).
On the tool-generated mutants, L1 kills 14 of the 15 that the designed suite
can reach; the remaining one, which replaces \(4ac\) by \((4/a)\,c\), is killed only
by the L3 test TC-QE-29 \((2,4,2)\), the one designed input on
\(\Delta=0\) with \(|a|\ge2\). The boundary layer adds no kill on either
population, but neither population contains a relational fault at the zero
tests that the boundary tests of \(q_2\) and \(q_3\) target. Of six such slips
executed separately, \(b\le0\) and \(c\le0\) survive every L1 test and are
killed only by L2 tests (\S\ref{sec:quad-exec}).

\subsection{Comparison of the Two Case Studies}
\label{sec:cross-case}

\paragraph{Domains.} The ATM has three integer inputs, two unbounded and one (\(\mathit{dailyUsed}\)) bounded below by \(0\), and two small categorical ones; the quadratic solver has three unbounded integer
inputs, tested within \([-100,100]^3\). Both output domains are flat (five
and six labels), but the quadratic one is reached through a two-level case
split.

\paragraph{Decision tables.} The ATM table has one extended-entry condition
over a single input (the amount classes) and two derived conditions over
several inputs; its infeasible columns come from a domain restriction
(\(\mathit{dailyUsed}\ge0\)), and its don't-care entries from a fixed rule
precedence. The quadratic table has one extended-entry derived condition
(the sign of \(\Delta\)); its infeasible columns come from algebraic
dependence between conditions, and its only don't-care entry from the
irrelevance of \(c\) in the linear case. Both tables are finer than the
minimal table on purpose: the ATM keeps the three invalid amount classes
apart (7 rules minimal, 9 used), and the quadratic table splits Case~A by
\(b=0\) and \(c=0\) (6 minimal, 10 used). In both, the rule count closes over
the feasible columns (56 of 64; 11 of 16). The exhaustive sweep confirmed completeness and non-overlap of the quadratic table; for the ATM, the executed witnesses check the implementation against the table, not the table itself.

\paragraph{Boundaries.} Table~\ref{tab:boundary-types} lists the conditions
and boundaries present in each case study.

\paragraph{Boundary interactions.} In the ATM, interaction is additive: a
threshold shifts by a constant (the fee), and two independent sums can be
tight at once. In the quadratic solver, interaction is non-linear: the
distance from the boundary depends jointly on all three coefficients. In
both, a boundary test of a derived condition had to be constructed by solving
the condition for one input given the others.

\paragraph{Mutation analysis.} ATM mutants are dominated by relational
operators, constants and evaluation order, reflecting a rule-based
specification; quadratic mutants are dominated by formula changes and
classification swaps. In both, the mutants that misbehave only at an
equality boundary (\(\mathit{balance}=T_5\) for M1; \(\Delta=0\) for N2, N3)
are killed only by tests that lie on that boundary.

\paragraph{Executed results.} Executed against an implementation, both
designs behaved alike in three respects: the decision table checks agreed with the rule counts and infeasibility claims, the analytical matrices
agree with execution (in all ATM cells and in 298 of 300 quadratic cells),
and the only tool-generated mutants that the designed suites do not kill
remove input checks outside the specified domain. They differ in where the
designed mutants are killed. In the ATM, decision table coverage kills 3 of
13, the boundary layer 7 more, and the don't-care expansion and mutation
feedback 3 more; on the seven mutants that the boundary layer adds, a size-matched random baseline kills 0.06 on average. In
the quadratic solver, decision table coverage already kills all 10 with the
chosen nominal inputs: N1--N3 because the rule QR5 is itself a test on \(\Delta=0\), N4, N5 and N7--N10 because any test of the branch they change kills them, and N6 only through the nominal value \((1,7,6)\).

\subsection{Lessons Common to Both Case Studies}
\label{sec:lessons}

\paragraph{From decision rules to boundaries.} A decision table states which
combinations of conditions must be tested; it does not say which input
within a combination to use. A nominal input passes whether or not the
boundaries of its rule are implemented correctly, so it cannot show that
they are. In the ATM, the nine nominal tests leave ten of the thirteen
designed mutants alive, and nineteen randomly chosen interior members of the
same rules leave on average 8.655 alive, where the nineteen boundary tests
leave 3. In these data the gain is that of boundary inputs over interior inputs, not of L2 over L1: L2 alone kills the same ten designed mutants as L1--L2. The two techniques divide the work: the table supplies the rules and their conditions, BVA supplies the inputs at which each condition changes its value. Where a rule is itself defined by an
equality, as \(\Delta=0\) is, its coverage test is already a boundary test.

\paragraph{Derived conditions need constructed tests.} Both case studies
contain conditions that are functions of several inputs
(\(\mathit{balance}\ge\mathit{amount}+\mathit{fee}\); the sign of
\(b^2-4ac\)). For such a condition \(\phi(x,y)\), the boundary \(\phi=0\) is
a lower-dimensional subset of the joint input space; varying \(x\) alone,
with \(y\) at a nominal value, meets it in at most finitely many points, and on the integers possibly in none (for \(\Delta=0\), only when \(4ac\) is a perfect square; \S\ref{sec:quad-combos}). Writing the derived condition as one
condition of the decision table, and taking its boundary values from the
derived quantity, places the tests on it. This is the setting of domain
testing \cite{whitecohen1980}, whose ON points lie on a border and OFF
points next to it; the \(T-1\), \(T\), \(T+1\) items of \(c_3\) and \(c_5\) play
these roles for linear borders, and \(\Delta=0\) is a non-linear one.

\paragraph{Don't-care entries hide behaviour.} A collapsed rule asserts that
some conditions do not matter. When that assertion rests on an evaluation
order, testing it requires setting the don't-care entry to the value that
would select another rule. In the ATM, the two modelled precedence reversals
(M11, M14) are killed by such tests and by no test of the coverage criterion
or the boundary layer; the random baseline kills them in 50\,\% and
78.5\,\% of its draws precisely because it fills don't-care entries at
random, often with failing values. The other four transpositions of two checks, including the adjacent R2/R3, are exposed even by the coverage test of DR4, TC-ATM-04, whose input fails R2, R3 and R5 together; for R1/R5 this depends on its nominal amount (\S\ref{sec:atm-exec}). This is why the don't-care expansion is reported as an extension of decision table testing rather than omitted.

\paragraph{A one-unit step can change the output category.} A derived
quantity can range over many values while the output stays constant, and
then change category at one step. \(\mathit{dailyUsed}+\mathit{amount}\)
yields an approval-eligible result for every value up to
\(20{,}000{,}000\), and Rejected\_DailyLimit at \(20{,}000{,}001\). In the
quadratic case, the reachable sequence \(\Delta=-3\to0\to5\) (TC-QE-28)
changes the output twice, NoRealRoots \(\to\) OneRepeatedRealRoot \(\to\)
TwoDistinctRealRoots, under unit steps of \(b\) alone: no real intersection
with the \(x\)-axis, then tangency, then two crossings. A suite that samples
only values far from every boundary cannot observe such a change.

\paragraph{What the mutation results show, and what they do not.} The layer
ablations (Tables~\ref{tab:atm-ablation} and~\ref{tab:quad-ablation}) report
which mutants each layer kills in these two mutant populations. They are
consistent with the premise of BVA that boundary tests detect faults that
interior tests do not: in the ATM the boundary layer kills seven designed
mutants beyond L1, while a random interior baseline of the same size kills
on average 0.06 of the same seven; and in the quadratic solver the relational
slips \(b\le0\) and \(c\le0\), which neither mutant population contains, are
killed only by boundary tests. They do not establish that the same holds for other
programs: the designed mutants were written with knowledge of the
boundaries the suites target (Section~\ref{sec:limitations}), the
tool-generated population is small, and the correlation between mutant
detection and real-fault detection is weak once suite size is controlled
\cite{papadakis2018}.

\section{Limitations}
\label{sec:limitations}
%=================================================================

\paragraph{Internal validity.}
\begin{itemize}
    \item The mutant-killing claims of \S\ref{sec:atm-matrix} and
    \S\ref{sec:quad-matrix} were derived by substitution and confirmed by
    executing mutant models and one implementation written for this report.
    Substitution and execution agree in 816 of 818 cells; the two
    disagreements (\S\ref{sec:quad-exec}) show that hand derivation alone is
    not reliable at this size.
    \item The designed mutants were written to probe the thresholds, the fee and the evaluation order of the ATM (M1--M14) and the \(\Delta=0\) boundary, the case split and the sub-case outputs of the quadratic solver (N1--N10). None of them changes the comparison at \(b=0\) or \(c=0\), so the quadratic boundary tests of \(q_2\) and \(q_3\) are measured only by the separately executed relational slips of \S\ref{sec:quad-exec}.
    The L3b tests were constructed to make exactly the rule pairs of M11 and
    M14 fail, and the L4 test exists because L1--L3 do not kill M8; these
    kills are by construction. The full analytically expected scores
    (\(13/13\), \(10/10\)) are therefore partly a designed-in property of the
    construction, not an unbiased comparison of boundary tests with interior
    tests.
    \item The six relational slips (\S\ref{sec:quad-exec}) and the six
    precedence transpositions (\S\ref{sec:atm-exec}) were also chosen by the
    designer of the suites, to probe the zero tests and the precedence. Each
    set covers one fault class completely (both directions at each of the
    three zero tests; every transposition of two checks), but neither is an
    independent sample of faults.
    \item The tool-generated mutants were not constructed together with the
    suites, but the implementation was. Two of its forms affect which
    mutants the tool produces: the if-statements that classify the sign of
    \(\Delta\) (\S\ref{sec:quad-exec}) and the rearranged form of R3
    (\S\ref{sec:atm-exec}). The population is small (22 and 21 killable
    mutants) and contains no operator that reorders rules or changes the
    modulus, so it cannot measure the contribution of L3b and L4.
    \item The 100\,\% Stryker scores are scores of the complete test projects,
    which include supplementary tests, properties and, for the quadratic
    solver, the exhaustive sweep. The designed suites alone reach 21 of 22
    (95\,\%) and 15 of 21 (71\,\%).
    \item The kill sets of N2 and N3 depend on the order in which the
    implementation tests the sign of \(\Delta\) (\S\ref{sec:quad-exec}). The
    quadratic L1 result depends on one nominal value (N6,
    \S\ref{sec:quad-matrix}), and the ATM L1 result on the balances chosen for DR8 and DR9 and, for the transposition R1/R5, on the amount chosen for DR4 (\S\ref{sec:atm-exec}).
    \item The random baseline uses one sampling scheme, stated in
    \S\ref{sec:atm-exec}; other schemes give other distributions. It is
    computed for the designed ATM mutants only: none was computed for the quadratic solver, and none for the tool-generated mutants, which are only available through Stryker runs.
    \item The per-layer Stryker scores were obtained by restricting the
    designed suite through an environment variable; the other test groups
    stayed in the run and were excluded from the count by test name. The
    Microsoft Testing Platform runner of Stryker.NET was marked as a preview
    at the time of the run.
    \item Equivalence of M4 was argued analytically and checked by execution
    over \(20{,}300{,}001\) amounts. For the other mutants, kill status was
    established against the suite inputs only; no search was made for
    further distinguishing inputs, and N1, for example, changes the output of
    inputs that the suite does not contain (\S\ref{sec:quad-matrix}).
    \item The implementation, the executable mutant models and the
    decision table oracles were written by the same party that designed the
    suites, with AI assistance, so the executed results test the consistency
    of design, models and implementation with the stated specification, not
    the specification's adequacy for a real ATM or solver. The
    arbitrary-precision oracle of the exhaustive sweep re-states the same
    formula as the implementation, so it detects overflow and branch-order
    errors but is not an independent check of the formula.
\end{itemize}

\paragraph{Construct validity.}
\begin{itemize}
    \item The don't-care expansion was applied only to the rule evaluated
    next in the precedence order, and only two reversals are modelled as
    designed mutants; the other four pairwise transpositions of the checks
    were executed separately (\S\ref{sec:atm-exec}). Expanding every don't-care
    entry would restore the full table (56 feasible ATM columns) and might
    expose faults in orderings that move more than two rules, which are not
    analysed here.
    \item Two conditions, \(c_5\) and \(q_4\), are derived from computed
    values (the fee; the discriminant), and both decision tables are refined
    beyond the minimal table (\S\ref{sec:atm-dt}, \S\ref{sec:quad-dt}). These
    are modelling choices of this report; a table built only from conditions
    on raw inputs, or the minimal table, would have different columns and a
    different L1 layer.
    \item The assumptions AS1--AS3 and QS1--QS2 settle points that the problem
    statements leave open. AS2 is what makes eight ATM columns infeasible; an
    accumulator that also subtracts reversed transactions could produce a
    negative \(\mathit{dailyUsed}\), which this report does not analyse.
\end{itemize}

\paragraph{External validity.} Both specifications are small, use integer
arithmetic only, and were implemented once; no real faults were available.
The observations about which layer kills which mutants therefore describe
these two case studies and their mutant populations, and are not claims
about decision table testing and BVA in general.

\section{Conclusion}
\label{sec:conclusion}
%=================================================================

This report applied decision table testing, boundary value analysis and
mutation analysis to two specifications with multi-variable behaviour, a
rule-based ATM validator and an algebraic classifier, and validated both
designs by execution. The research questions of Section~\ref{sec:intro} can
be answered as follows, within the limits of Section~\ref{sec:limitations}.

\textbf{RQ1.} Conditions over several inputs were kept as conditions of the
table (the daily sum, the fee-adjusted balance, the sign of \(\Delta\)), and
single-input conditions with several outcomes were written as extended-entry
conditions whose entries partition the input's domain. The infeasible
columns followed from a domain assumption in the ATM and from algebraic
dependence in the quadratic solver, and were proved. The rule counts close
over the feasible columns (56 of 64 for nine ATM rules; 11 of 16 for ten
quadratic rules); this is a necessary condition. For the quadratic table, the exhaustive sweep of all \(8{,}120{,}601\) triples of the test range confirmed completeness and non-overlap, including the absence of inputs in infeasible columns; for the ATM, the executed witnesses check the implementation against the table. Both tables are refinements of minimal tables of 7 and 6
rules; the quadratic refinement by \(b=0\) and \(c=0\) exposes two rules,
QR7 and QR10, in which a zero coefficient fixes the sign of \(\Delta\).

\textbf{RQ2.} 3-value BVA added 19 ATM and 17 quadratic tests. In the ATM,
decision table coverage alone killed 3 of 13 designed and 14 of 22
tool-generated mutants; with the boundary layer the counts rose to 10 and 21,
while a random baseline of the same size from the same rules killed 4.345
designed mutants on average, and 0.06 of the seven that the boundary layer
adds. The added kills were the relational mutants at
equality boundaries and the mutants that shift a threshold, including the
fee, which is visible only when the balance condition is analysed in the
external column. In the quadratic solver, decision table coverage already
killed all ten designed mutants with the chosen nominal inputs: N1--N3 because the rule QR5 is itself a test on \(\Delta=0\), the others because any test of the branch they change kills them (N6 only through its nominal input). The boundary layer added
no kill on either population, but neither population contains a relational slip at the zero tests, at which its tests are aimed; of six relational slips at these zero tests, executed separately, two (\(b\le0\), \(c\le0\)) survive one test per rule and are killed only by boundary tests.

\textbf{RQ3.} The two modelled precedence reversals (M11, M14) were killed
only by the don't-care expansion, which lies outside the coverage criterion
of decision table testing; the other four transpositions of two checks,
executed separately, are already exposed by the coverage test of DR4, whose
input fails three rules at once (for R1/R5 only through its nominal amount). One designed mutant, a wrong modulus (M8),
needed a
test from mutation feedback, and a related wrong modulus, \(25{,}000\),
survives the whole suite. The boundary combinations added no kill in either
case study, except one tool-generated quadratic mutant, which was killed only
by a further point on \(\Delta=0\). The tool-generated mutants contain no
reordering or modulus fault, so the contribution of L3b and L4 is shown only
on designed mutants, by construction.

Across both case studies, every test case answers the question ``why does
this test exist?'' by pointing to a decision rule, a boundary coverage item,
a boundary combination or further point on a derived boundary, a don't-care
expansion, or a mutant that no earlier test kills, and the executed
results report what each of these sources contributes, including the cases
in which it contributes nothing.

\paragraph{Future work.} Three extensions would test how far these
observations generalise. First, the layer ablation should be repeated on
larger mutant populations that the suites were not designed against, for
example mutants generated from several independent implementations, with
operators that reorder statements, and with size-matched baselines for the
tool-generated mutants as well. Second, the don't-care expansion was limited
to the rule evaluated next; expanding all don't-care entries would show
whether orderings that move more than two rules hide further faults, and the
granularity condition should be
tested against every divisor class of the step (here \(60{,}000\) and
\(75{,}000\)). Third, the method should be applied to specifications with
more interacting conditions, where the full table is too large to enumerate
and the choice of which columns to expand becomes a design decision in its
own right.
